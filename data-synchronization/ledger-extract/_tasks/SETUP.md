> py-db-schema spins up a fresh Docker PostgreSQL container (`postgres:17`), applies all migrations from `migrations_path` into it, introspects the resulting schema, then tears the container down — it does **not** connect to the existing `FULCRUM_DB_*` instance. Requires Docker to be running. No env vars needed. `connect_database` is the name of the ephemeral database created inside the container — it does not need to match `FULCRUM_DB_NAME`.

## `ledger_data_checksums` table schema (migration 0001)

Tracks the last known state of every extracted row. Drives hash comparison and soft-delete detection.

| Column | Type | Notes |
|--------|------|-------|
| `entity` | `TEXT NOT NULL` | e.g. `'categories'`, `'accounts'` |
| `natural_key` | `TEXT NOT NULL` | Encoded key — see per-entity encoding below |
| `row_hash` | `TEXT NOT NULL` | SHA-256 of source row content from last run |
| `last_seen_at` | `TIMESTAMPTZ NOT NULL` | When this key was last confirmed present in the sheet |

`PRIMARY KEY (entity, natural_key)`

Rows are deleted from this table when the corresponding entity row is soft-deleted — `ledger_data_checksums` only holds currently active keys.

---

## `job_execution_details` table schema (migration 0001)

Stores the last-seen spreadsheet modified time to enable the early-exit optimisation.

| Column | Type | Notes |
|--------|------|-------|
| `job_name` | `TEXT NOT NULL` | e.g. `'ledger-extract'` |
| `last_sheet_modified_at` | `TIMESTAMPTZ` | Last spreadsheet modified time seen by this job; NULL on first run |
| `ran_at` | `TIMESTAMPTZ NOT NULL` | When the job last ran |

`PRIMARY KEY (job_name)`

## Sync-status model (all entities)

All entities use a GAS-stamped `sync_status` column. The sheet is the source of truth for intent; the DB reflects what has been applied. There is no hash comparison, no `ledger_data_checksums` involvement, and no soft-delete pass — when a user deletes a row via the app, GAS sets `record_status = 'deleted'` and `sync_status = 'update-pending'`; the extract job picks it up via the normal update path.

**Status values**

| Value | Set by | Meaning |
|---|---|---|
| `create-pending` | GAS | Row is new — not yet in DB |
| `update-pending` | GAS | Row has changed — DB is stale |
| `in-sync` | Extract job | Row matches DB — skip on next run |
| `create-failed` | Extract job | Last create attempt failed — will retry |
| `update-failed` | Extract job | Last update attempt failed — will retry |

**How a run works for each entity**

1. Read sheet in batches of up to 1000 rows. If the first batch returns 0 rows, abort with `RuntimeError` — do not proceed.
2. For each row: skip if `in-sync`; skip with warning if `sync_status` is missing or unrecognised (do not write back).
3. For `create-pending` / `create-failed`: INSERT via `ON CONFLICT DO UPDATE`. On success write back `in-sync`. On known integrity error (`UniqueViolation`, `ForeignKeyViolation`, `CheckViolation`, `NotNullViolation`) rollback and write back `create-failed` + human-readable `sync_notes`. All other exceptions propagate and abort the job.
4. For `update-pending` / `update-failed`: UPDATE by natural key with `RETURNING id`. If 0 rows returned, fall back to INSERT path. On success write back `in-sync`. On known integrity error rollback and write back `update-failed` + `sync_notes`.
5. Each row is committed independently before the next row begins.
6. All write-backs for the batch are accumulated in a `list[WriteBack]` and flushed in a single `batch_update_rows` API call at the end of the batch.

For most entities there is no soft-delete pass — removed rows are left in the DB with `record_status = 'deleted'` (set by GAS before extract). **Exception:** the transactions module runs two post-row soft-delete passes after processing all rows: one for `counterparty_master` (marks orphaned counterparties `deleted` when no active transaction references them) and one for `beneficiaries_master` (same for beneficiaries with no active transaction junction rows). Each pass is committed independently.

## Incremental load approach

`get_modified_time()` operates at **spreadsheet level**, not tab level. The early-exit only fires when nothing in the entire spreadsheet has changed. Any edit to any tab (including unrelated tabs) will cause all enabled entities to be processed.

Every run is structured in three phases:

**Phase 1 — Job state (runs first, standalone)**
1. Bootstrap: `INSERT INTO job_execution_details (job_name, last_sheet_modified_at, ran_at) VALUES ('ledger-extract', NULL, '1970-01-01T00:00:00Z'::timestamptz) ON CONFLICT (job_name) DO NOTHING` — ensures a row exists on first run; sentinel `ran_at` is immediately overwritten by Phase 3 on success
2. Read `last_sheet_modified_at` from `job_execution_details WHERE job_name = 'ledger-extract'`
3. Call `SheetsClient.get_modified_time()` and cache the result — it is reused in Phase 3. If an error occurs (API or network error), `get_modified_time()` raises — the exception propagates and aborts the job run; do not proceed, do not update `ran_at`. If the cached result equals `last_sheet_modified_at`, run `UPDATE job_execution_details SET ran_at = now() WHERE job_name = 'ledger-extract'` and exit (intentional — `last_sheet_modified_at` already equals the current sheet modified time; the next run will compare against the same value and early-exit again if the sheet is still unchanged). Note: on first run `last_sheet_modified_at IS NULL` — NULL never equals a real timestamp, so the job always proceeds on first run.

**Phase 2 — Entity extraction (each entity in sequence)**
4. For each enabled entity (categories → accounts → transactions → subscriptions):
   a. Read sheet in batches of up to 1000 rows. If the first batch returns 0 rows, abort immediately with `RuntimeError` — never proceed on an empty first read.
   b. For each row: route by `sync_status` per the sync-status model above. Each row is committed independently. Write-backs are accumulated per batch and flushed in a single `batch_update_rows` call at the end of the batch.

**Phase 3 — Finalise**
5. Update job_execution_details using the `get_modified_time()` value cached in Phase 1:

```sql
INSERT INTO job_execution_details (job_name, last_sheet_modified_at, ran_at)
VALUES ('ledger-extract', $1, now())
ON CONFLICT (job_name) DO UPDATE
    SET last_sheet_modified_at = EXCLUDED.last_sheet_modified_at,
        ran_at = EXCLUDED.ran_at
```
   where `$1` is the timestamp returned by `get_modified_time()` in Phase 1 step 3.

> **Partial failure:** If the job fails before Phase 3 completes, `last_sheet_modified_at` is not updated. The next run re-processes all entities from Phase 2, which is safe because all entity upserts are idempotent via `ON CONFLICT DO UPDATE`.

> **Single-instance assumption:** The job is designed to run as a single instance at a time (e.g. scheduled cron). Concurrent runs are not safe.

## Build order

Build one entity at a time in this order. Each entity is self-contained — migration, transform, database helper, extractor wiring.

1. `categories` — depends on `account_types` (0002); shared infrastructure `ledger_data_checksums` + `job_execution_details` are in (0001)
2. `accounts` — no dependencies
3. `transactions` — references accounts and categories (FK decision pending)
4. `subscriptions` — references accounts and categories (FK decision pending)
